# Deployment

> The Dockerfile and compose file have **not been built** here, because this machine has no Docker. CI builds the image
> on every pull request, but it hasn't run yet. The production bundle itself was booted directly with Node, using
> production settings.

## Free staging on Render

`render.yaml` sets up a staging site that costs nothing. It uses Render's native Node runtime, not Docker, and needs
no card as far as Render's docs say, though they don't state it outright. Without a payment method, going over a free
allowance suspends the service instead of charging you.

| Piece | Free service |
| --- | --- |
| App | Render web service, `plan: free` |
| Redis | Render Key Value, `plan: free` |
| MongoDB | MongoDB Atlas M0 |
| Media | Cloudinary free plan |

1. Merge to `main`, which is the branch the Blueprint deploys.
2. Create an Atlas M0 cluster, ideally in Singapore to sit near the app, and a database user. Allow access from
   `0.0.0.0/0`, because Render's free plan has no fixed outbound address. That makes the database password the only
   barrier, so make it long and random. Add `/strata` to the connection string, before any `?`. Give the user `readWrite` on
   `strata` only, never an admin role. Production refuses to start without TLS or a database name.
3. Create a Cloudinary account and note the cloud name, API key and API secret.
4. In Render, choose New, then Blueprint, and pick this repository. Paste the four values it asks for.
5. Open `/api/health` on the new address, and expect `{"status":"ok"}`.

The app takes its address from `RENDER_EXTERNAL_URL`. `JWT_SECRET` and `MEDIA_SIGNING_SECRET` are generated by Render.
For push notifications, add the three `VAPID_*` variables to the service by hand.

### What free costs in behaviour

| Limit | Effect on Strata |
| --- | --- |
| Sleeps after 15 minutes without traffic, and takes about a minute to wake | The first visit after a quiet spell is slow, and open sockets drop and reconnect |
| Nothing runs while asleep | Digests, acknowledgement deadlines and escalations wait until the next visit wakes the service. They run late rather than being lost, because delivery state lives in MongoDB |
| 750 instance hours a month per workspace | Enough for one service left running. A second free service could use them up, and services then stop until the next month |
| Key Value isn't saved to disk | Redis can vanish without warning. Delivery keeps running, because its clock is a timer in the app. Rate limits reset, and pending block compaction waits for the next update |
| No disk | Uploads have to go to Cloudinary |
| One instance, no background workers | Hence `ROLE=all` |
| Outbound ports 25, 465 and 587 are blocked | Email, once it's built, has to use a provider's HTTP API rather than SMTP |

Start with about 25 people or 50 sockets, and don't pass 100 sockets before measuring on Render. The 0.1 CPU is likely
to run out before the 512 MB does. This suits testing with a few people. Delivery timing can't be relied on while the service sleeps, so a real launch
needs a paid instance or another always-on host.

`TRUST_PROXY_HOPS=1` is an assumption about Render's proxies. After deploying, check that rate limits apply per person
and not to everyone at once. Too low a value makes all traffic look like one address.

## What you need

| Service | Notes |
| --- | --- |
| Node 22+ host with **long-lived connections** | Serverless platforms can't hold WebSockets |
| MongoDB 6+ | MongoDB Atlas works. A replica set isn't required for correctness |
| Redis 6.2+ | Required in production. Don't enable eviction, because BullMQ needs its keys kept |
| Cloudinary | For media. See below |
| TLS terminator | Required. Refresh cookies are `Secure` |

## Processes

Run one image in two roles, so that scaling the API doesn't multiply background work:

| Role | Command | Scale |
| --- | --- | --- |
| API | `ROLE=api node dist/main.js` | Horizontally |
| Worker | `ROLE=worker node dist/main.js` | One or more. Work is claimed atomically, so extras are safe |

`ROLE=all` runs both in one process, which suits small deployments.

## Configuration

`.env.example` documents every variable. Production refuses to start unless:

- `REDIS_URL` is set
- `APP_URL` uses https
- `CORS_ORIGINS` has no wildcard
- `JWT_SECRET` and `MEDIA_SIGNING_SECRET` are different, and at least 32 characters
- Cloudinary credentials are present, if that provider is selected

Generate secrets with:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

Keep secrets in your platform's secret store. Rotating `JWT_SECRET` signs everyone out of their current access token,
and they recover through their refresh cookie.

## Reverse proxy

- Set `TRUST_PROXY_HOPS` to the exact number of proxies. Too high lets clients spoof their IP and dodge rate limits.
- Forward WebSocket upgrades for `/socket.io`.
- Allow request bodies of 25 MB on `/api/media`, if using the disk provider.

### More than one API node

Tested with two real server processes sharing MongoDB and Redis. The client tries WebSocket first and can fall back to long-polling. Polling needs **sticky sessions**, so either enable
them on your load balancer, or set the client to `transports: ['websocket']` in `apps/web/src/realtime/socket.ts`.

## Serving the web client

Either set `WEB_DIST` to the built `apps/web/dist` and let the API serve it, which gives you the CSP in `app.ts`, or put
it on a CDN. With a CDN on another origin you'd need to add that origin to `CORS_ORIGINS`, and the `SameSite=Strict`
cookies mean API and client must still share a site.

## Media with Cloudinary

**Not yet verified against a live account.** The integration is complete, but no credentials were available.

1. Set `MEDIA_PROVIDER=cloudinary` and the three `CLOUDINARY_*` variables.
2. In Cloudinary settings, restrict unsigned uploads, and keep strict transformations on.
3. Upload a file through the app and confirm that it's stored as type `authenticated`.
4. Confirm the raw Cloudinary URL fails without a signature.

Note that `disk` storage doesn't work with more than one API node, unless `MEDIA_DIR` is a shared volume.

## Web Push

**Not yet verified with a real browser subscription.**

```bash
pnpm --filter @strata/server exec web-push generate-vapid-keys
```

Set `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT`. People then opt in from Settings. Without these keys,
in-app notifications still work.

## Operations

| Task | Approach |
| --- | --- |
| Health | `GET /api/health` returns 503 when MongoDB is unreachable |
| Logs | JSON on stdout, through pino. Tokens and passwords are redacted |
| Backups | Back up MongoDB. It's the source of truth. Redis needs no backup |
| Redis loss | Delivery keeps running on the app's own timer, reading due work from MongoDB. While Redis is down, sign-in, registration and guest links return 503 so that their limits can't be bypassed, and other rate limits are skipped. Everything recovers by itself |
| MongoDB loss | Requests fail within about 5 seconds and health returns 503, so Render restarts the app after a minute. It reconnects by itself |
| Shutdown | SIGTERM drains sockets and workers |
| Indexes | Mongoose builds them on start. For large collections, build them ahead of a deploy instead |
